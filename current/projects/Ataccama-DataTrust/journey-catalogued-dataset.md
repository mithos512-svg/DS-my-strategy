# Путешествие объекта «закаталогизированный датасет в Ataccama» - модель v0.1

**Статус:** первая версия (actionable, не совершенная - по R2.6:7 «первая версия
будет несовершенной, но уже рабочей»). Создана 16.10.2026 по запросу
пользователя. Шаги процесса Ataccama ONE взяты как типовые - **подлежат
сверке с реальной настройкой на работе** (см. «Открытые вопросы»).

**Метод:** онтология путешествия объектов R2.6:7 (объект путешествия →
состояния → события → узлы графа создателей → контактёры → работа vs такт
работы → путь → поток) + измерение по R2.6:4. Сверка через FPF Library
(снапшот 20261015T182921Z, актуален upstream на 16.10): `A.15.PROD`
(три вопроса производства: участие работы / начало существования сущности /
завершение), `A.3.4` (трансформация - что реально изменилось), `A.15.1`
(работа), `E.24.PUB` (публикация = доступность аудитории, отдельная от
завершения).

## 1. Объект путешествия - и первая ловушка

R2.6:7 требует определить, **система это или эпистема**. Здесь их два, и
их нельзя смешивать:

| Объект | Тип | Где живёт |
|---|---|---|
| **Датасет** (таблица/файл в источнике) | физический объект, носитель данных | SAP / GCP / BI / файловое хранилище |
| **Каталожная запись** (catalog item) о датасете | **эпистема** - описание датасета | Ataccama ONE Catalog |

«Закаталогизированный датасет» = датасет, **о котором существует каталожная
запись в целевом состоянии**. Объект путешествия - **каталожная запись**
(эпистема), а датасет - её *референт*. Это важно потому, что:

- состояния меняет запись, а не датасет (датасет может не меняться вовсе);
- по `A.15.PROD` вопрос «когда закаталогизированный датасет начал
  существовать» - это вопрос о записи, а не о таблице в SAP;
- по `E.24.PUB` «опубликовано в каталоге» - отдельное событие доступности
  аудитории, не совпадающее с «запись заполнена».

## 2. Три вопроса A.15.PROD, применённые к объекту

FPF запрещает сворачивать производство в одно утверждение «каталог сделал
датасет». Три отдельных локальных утверждения:

| Вопрос A.15.PROD | Применение к каталожной записи | Что НЕ следует из него |
|---|---|---|
| **Участие работы:** какая работа - целая работа каталогизации, а какая - её часть | Работа «каталогизировать датасет X» состоит из частей: импорт метаданных, профилирование, классификация, назначение владельца, DQ-привязка, lineage, утверждение. Каждая часть - своя работа (`A.15.1`), а не «весь каталог» | Что импорт метаданных = каталогизация. Это проходит проверку только как *часть* |
| **Начало существования сущности:** когда «закаталогизированный датасет» впервые существует | Нужно **правило идентичности** (`productIdentitySpecification`). Кандидат: «каталожная запись с уникальным ID, связанная с физическим активом, в состоянии ≥ Approved». Пока правило не выбрано - вопрос заблокирован (`identity-governor blocker`). **Важно:** по A.15.PROD «назначенный идентификатор - не критерий начала существования»: запись с ID после импорта - ещё не закаталогизированный датасет | Что появление записи после автоимпорта = «датасет закаталогизирован» |
| **Завершение:** какое состояние удовлетворяет критерию, и что закрывает работу | Два отдельных утверждения: (а) запись в состоянии «Certified» по чеклисту полноты; (б) работа каталогизации закрыта - кем/чем (steward approval? автоправило?). Без явного «закрывающего» правила - `missing-governor[production-work-completion]` | Что «опубликовано для бизнеса» = «завершено». Публикация - E.24.PUB, своя претензия |

**Практический вывод:** у команды, скорее всего, нет явного ответа на вопросы
2 и 3 - именно это и даёт разброс «что считать закаталогизированным» между
отделами (связь с R2.6:5 - разные шкалы у разных ролей).

## 3. Методологический путь: состояния и события

«Методологическое время» (R2.6:4) - без часов, только последовательность
состояний, которые запись *не может не пройти*. События - моменты, по которым
мы **узнаём**, что состояние достигнуто (R2.6:7: описание события должно
позволять это определить).

| # | Состояние записи | Событие-вход (как узнаём) | Узел графа создателей (функц. локация) | Контактёр (роль) | Работа по методу | Типовой откат |
|---|---|---|---|---|---|---|
| 0 | **Датасет существует, записи нет** (вход) | - | источник (SAP/GCP/BI) | владелец системы-источника | - | - |
| 1 | **Источник подключён** | коннектор в статусе Connected, первый успешный сканинг | Ataccama ONE: Sources | Data Engineer / Platform | настройка коннектора | креды протухли → 0 |
| 2 | **Метаданные импортированы** (запись существует технически, ID присвоен) | catalog item появился, status = Discovered/Imported | Catalog | автомат + Data Engineer | discovery / metadata scan | схема изменилась → повторный импорт |
| 3 | **Профилировано** | profiling job завершён, статистики видны | Catalog / Profiling | автомат, инициирует Data Engineer / Steward | profiling | ошибка доступа к данным → 2 |
| 4 | **Классифицировано и описано** | термины глоссария и классификация назначены, описание заполнено | Catalog / Business Glossary | Data Steward | классификация, описание, связь с терминами | спор о термине → остаётся в 4 (Wait) |
| 5 | **Владелец назначен** | поле Owner/Steward заполнено, владелец подтвердил | Catalog / Ownership | Data Governance Lead ↔ бизнес-владелец | назначение + подтверждение | владелец отказывается → эскалация (Wait!) |
| 6 | **DQ-привязка сделана** | DQ-правила назначены, первый прогон есть | DQ module | Data Steward + DQ analyst | настройка правил, прогон | правила падают → доработка |
| 7 | **Lineage построен** | upstream/downstream видны в lineage view | Lineage module | Data Engineer | lineage scan / ручная привязка | источник не поддержан → ручной lineage или пропуск |
| 8 | **Утверждено / Certified** | approval workflow завершён, status = Approved/Certified | Catalog / Workflow | Data Governance Lead / Steward (approver) | ревью по чеклисту полноты | возврат на доработку → 4-7 |
| 9 | **Опубликовано для потребителей** (E.24.PUB) | запись видима целевой аудитории (self-service), доступ открыт | Catalog / Access | Platform + Governance | публикация, права | аудитория не видит → не опубликовано, хотя certified |
| 10 | **Используется** (выход за границу «предприятия каталогизации») | первый поиск/запрос аналитика к записи, первое использование в отчёте | потребители | аналитик / бизнес | - | - |

Состояния 1-3 могут идти автоматически и быстро; **4, 5, 8 - узлы, где работа
переходит в ожидание** (координация с ролями вне команды данных). Это прямо
отвечает на вопрос 15.10 про координацию: она здесь - явные состояния, не фон.

## 4. Работа vs такт работы (R2.6:7)

«Работа завершена, когда есть нужный объект в нужном состоянии; такт работы
может завершиться и без этого». Для каждого узла 4-8 стоит считать **число
тактов** до достижения состояния:

- «отправлено владельцу на подтверждение» - такт; «владелец подтвердил» -
  работа завершена. Три письма без ответа = три такта, работа не завершена.
- По R2.6:7, если тактов больше одного регулярно - менять либо исполнителя,
  либо метод (например, ввести чеклист готовности к утверждению вместо
  переписки - связь с НЭП про чеклисты 14.10 и R2.6:2).

## 5. Пути и поток

- **Путь** (реальная траектория одной записи) будет отклоняться от
  методологического: часть датасетов идёт 2 → 4 → 8 без профилирования и DQ
  (референсные справочники), часть зависает в 5 на недели, часть возвращается
  из 8 в 4.
- **Поток** - все записи одного класса (например, «датасеты домена продукт»).
  Метрики потока по R2.6:4: выпуск (записей в состоянии 9 за неделю),
  скорость до результата (0 → 9), **узел с максимальным Wait Time =
  ограничение** (гипотеза: 5 или 8). Воздействовать на ограничение, не на
  скорость автоимпорта.
- Критерий roadmap «первый сертифицированный датасет - продуктовый каталог»
  (Фаза 1) - это один объект, прошедший до состояния 8; roadmap не говорит,
  нужно ли 9. По A.15.PROD это разные претензии - стоит уточнить в roadmap.

## 6. Что измерять (минимум, по R2.6:4 и TameFlow из R2.6:2)

| Метрика | Как снять в Ataccama | Зачем |
|---|---|---|
| Дата входа в каждое состояние 2-9 на запись | статусы/аудит-лог catalog item, workflow history | Flow Time по узлам |
| Число тактов в узлах 5 и 8 | история workflow (returns, reminders) | где работа не завершается с первого раза |
| Доля записей, вернувшихся из 8 в 4-7 | workflow history | качество подготовки к утверждению |
| Wait Time в 4, 5, 8 | разница дат «отправлено» / «подтверждено» | ограничение потока |

## 7. Открытые вопросы (сверить с реальной настройкой)

1. Какие **статусы catalog item** реально включены в вашем Ataccama ONE
   (Discovered / Approved / Certified / Deprecated - или кастомные)? Таблица
   выше использует типовые.
2. Есть ли **approval workflow** (состояние 8) как настроенный процесс, или
   «утверждено» - устная договорённость? Если второе - закрывающего правила
   по A.15.PROD нет, и «certified» нечем доказать.
3. **Правило идентичности** «закаталогизированного датасета»: с какого
   состояния вы сами считаете, что он существует - 2, 8 или 9? Нужен один
   ответ, записанный, иначе разные роли будут спорить (R2.6:5).
4. Lineage (7) - обязательное состояние перед 8 или параллельная ветка?
5. Кто **аудитория** публикации (9) и через какую форму - self-service UI,
   экспорт, Data Trust Dashboard?
