# DPF и LPF по Data Lineage

> Проверено через реальный FPF-паттерн `E.4.DPF` (Domain Principle Framework
> Authoring, читан напрямую из /mnt/project/FPF-Spec_9.md, правило от 23.08).
> Домен переключён с Data Quality на Data Lineage 30.08 (решение пользователя) -
> команда внедряет новую capability Data Lineage, нужны DPF/LPF для
> документирования принципов и протоколов работы с ней.

## Шаг 1 (E.4.DPF:4, п.1-2) — читатель, задача, граница

**Читатель:** участник команды/платформы, работающий с системами, где данные
передаются между источником и потребителем (не вся организация - конкретные
владельцы/инженеры данных, вовлечённые во внедрение capability).

**Типовая задача:** отследить, откуда взялась конкретная цифра в отчёте, или
понять, какие downstream-системы сломаются при изменении upstream-поля - это
и есть причина внедрения capability (со слов пользователя, 30.08).

**Граница non-use:** не для общей архитектуры данных, не для качества данных
как такового (отдельная, приостановленная тема) - именно происхождение/путь
данных.

## Шаг 2-4 (E.4.DPF:4, п.3-4) — источник

Использован DAMA-DMBOK как "maintained synthesis or guide" (та же source
situation, что и для DQ ранее). Проверено через web_search (не было в базе на
момент среза) - в DAMA-DMBOK **Data Lineage не отдельная область знаний**, а
часть **Metadata Management**. Официальное определение (DAMA-NL, 2020):
"метаданные, которые идентифицируют источники данных и трансформации, через
которые они прошли до текущей точки применения".

## Шаг 5 (E.4.DPF:4, п.5) — провизорные pattern-карточки

> Расширено до 5 карточек вместо стандартных "1-4" (E.4.DPF:4, п.5) - карточка
> 5 добавлена пользователем явно (30.08) как отдельная, содержательно
> отличающаяся проблема, а не искусственное дробление одной карточки.

| # | Проблема | Решающий ход |
|---|---|---|
| 1 | Нельзя проследить, откуда взялась цифра в отчёте (backward lineage) | Хранить lineage-метаданные: источник + все трансформации до текущей точки, для каждого критичного значения |
| 2 | Непонятно, что сломается при изменении upstream-поля (forward lineage) | Хранить lineage как граф связей в прямом направлении - impact analysis до изменения, не после инцидента |
| 3 | Неясно, кто отвечает за то, чтобы lineage вообще фиксировался | Явная роль (steward) для конкретного датасета/пайплайна, а не размытая ответственность |
| 4 | Lineage фиксируется не на том уровне детализации (только таблицы, без колонок) - ложная уверенность в impact analysis | Явно определить нужную granularity (колонка vs таблица) для каждого критичного датасета до выбора инструмента |
| 5 | Низкое качество данных обнаружено, но неясно - возникло на этом этапе или унаследовано из upstream (предложено пользователем, 30.08) | Использовать граф lineage для трассировки проблемы назад до точки происхождения - различать "внесено здесь" vs "унаследовано" |

Карточка 5 не из фиксированного списка DAMA (у lineage, в отличие от DQM, нет
готового перечня "6 задач") - это собственная сборка из реальных примеров
пользователя + типовых активностей Metadata Management. Карточка 5 явно
мостит к приостановленному проекту Data Quality - не как отдельный проект, а
как одно из применений lineage.
