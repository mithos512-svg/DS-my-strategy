# LPF: Принципы и протоколы Data Lineage — Supply Planning pipeline

> Решение framework scale test (30.08, `E.4.DPF:4.0`): это **LPF** (локальная
> адаптация под конкретную команду/платформу), не DPF (заявка на весь домен
> Data Lineage). Причина: реальная задача — задокументировать принципы для
> одной команды, внедряющей capability, а не покрыть домен целиком.

## Читатель, задача, граница (Шаг 1, E.4.DPF:4)

**Читатель:** участник команды/платформы, работающий с системами, где данные
передаются между источником и потребителем.

**Типовая задача:** отследить происхождение цифры в отчёте или понять, что
сломается при изменении upstream-поля.

**Граница non-use:** не для общей архитектуры данных, не для качества данных
как такового (отдельная, приостановленная тема — data quality).

## Источник (Шаги 2-4)

**Внешняя зависимость (названа явно, как требует E.4.DPF:4.0):**
DAMA-DMBOK2 (2-е издание, 2017, издатель DAMA International), раздел
Metadata Management. Используется как концептуальная основа для всех 5
карточек ниже. Условие актуальности: остаётся действующей до выхода
DMBOK 3.0 (заявлен DAMA International на 2027) — на момент этого документа
не выпущен, зависимость актуальна.

## Провизорные pattern-карточки и материальные связи (Шаг 5 + связи)

| # | Проблема | Решающий ход | Связь с другими карточками |
|---|---|---|---|
| 1 | Нельзя проследить, откуда взялась цифра в отчёте (backward lineage) | Хранить lineage-метаданные: источник + все трансформации до текущей точки | Ядро механики lineage, симметрично карточке 2 |
| 2 | Непонятно, что сломается при изменении upstream-поля (forward lineage) | Хранить lineage как граф связей в прямом направлении - impact analysis до изменения | Ядро механики lineage, симметрично карточке 1 |
| 3 | Неясно, кто отвечает за фиксацию lineage | Явная роль (steward) для каждого датасета/границы систем | Предпосылка для 1 и 2 - без steward'а граф не поддерживается актуальным |
| 4 | Lineage не на том уровне детализации (только таблицы, без колонок) | Явно определить нужную granularity для каждого критичного датасета | Конфигурационное решение, применяется к 1 и 2 одновременно |
| 5 | Низкое качество данных - неясно, откуда: с этого этапа или унаследовано | Использовать граф lineage для трассировки назад, различать "внесено здесь" vs "унаследовано" | Применение карточки 1 к сценарию расследования DQ, не отдельный механизм |

## Представительное применение (Шаг: representative application)

**Пайплайн Supply Planning** (со слов пользователя, 30.08):

SAP (мастер-данные) → Google Cloud (drivers) → o9 (planning tool, расчёт) →
Google Cloud (результаты расчёта) → Power BI (отчётность).

| Карточка | Применение к этому пайплайну |
|---|---|
| 1 (backward) | Проследить цифру в Power BI назад: выгрузка GCP → расчёт o9 → исходные drivers/мастер-данные SAP |
| 2 (forward) | Что сломается в Power BI/отчётах при изменении поля мастер-данных в SAP |
| 3 (ответственность) | SAP, GCP, o9 и Power BI - вероятно, разные владельцы; нужен явный steward на каждой границе системы |
| 4 (granularity) | Мастер-данные (SAP) - вероятно нужен уровень поля; drivers (GCP) - возможно, уровень датасета; решение принимается явно для каждой границы |
| 5 (DQ-трассировка) | Если цифра в отчёте выглядит неверной - понять, возникло ли это в SAP, в drivers GCP, в логике расчёта o9, или в выгрузке |

Этот пример проходит через все 5 карточек - удовлетворяет требованию "one
representative application that crosses the patterns and problem-family sets
needed for the first use" (`E.4.DPF:4.0`).

## Граница поддержки (maintenance boundary)

Поддерживается командой/платформой, внедряющей capability (тот же читатель,
что и в Шаге 1). Условие пересмотра: (а) появление проблемного случая, не
покрываемого текущими 5 карточками, или (б) выход DMBOK 3.0 (2027), если он
материально меняет содержание раздела Metadata Management по data lineage.
