## Обучающая заметка: план работ по business justification (аутсорс vs инсорс) — применение FPF C.11 + DAMA (2026-08-28)

**Что это:** загруженный рабочий файл `business_justification_workplan.xlsx` - подробный план работ (7 фаз) для подготовки обоснования решения о переводе поддержки с аутсорса на инсорс.

**Структура плана (7 фаз):**

0. Учреждение полномочий - decision maker, делегирование, ответственный за качество данных решения
1. Координаты сравнения (CharacteristicSlotSet) - 5 критериев (стоимость, риски, контроль, время выхода на самостоятельность, качество поддержки), проверка на 3 контрольных кейсах
2. Набор вариантов (OptionSet) - Outsource/Insource/Hybrid, условия по каждому, закрытие набора
3. Калибровка шкалы (ScaleBindingSet) - тип шкалы по каждой координате, калибровочная сессия
4. Данные и модель последствий (OutcomeModel) - baseline-данные, проверка качества данных (accuracy/completeness/consistency), прогноз по вариантам с пометкой факт/прогноз
5. Проверка перед решением - 3-месячный пилот, обновление модели измеренными данными
6. Правило выбора и решение (ChoiceRule → ChoiceResult) - типизированный результат (choose now/reject/probe again/reroute), архив истории решений
7. Оформление документа - сбор всех объектов, разметка достоверности данных, согласование, утверждение

**Связь с моими проектами (по смыслу, зафиксировано пользователем при загрузке файла):**

Прямое пересечение с текущей работой над **DPF/LPF по data quality** (`current/projects/DataQuality_Usefulness_Evaluation/`):

- Тот же паттерн `FPF C.11 Decision Theory`, что уже применялся в завершённом `approach.md` (оценка полезности внедрения системы контроля качества данных).
- Те же роли DAMA-DMBOK - Data Owner/Steward/Custodian - что и в 4 pattern-карточках, закрытых 25.08 в `dpf-lpf-outline.md`.
- Фаза 4 (проверка качества данных: accuracy/completeness/consistency) - прямая практическая иллюстрация карточки №3 из dpf-lpf-outline ("называть конкретное измерение прежде чем ставить правило").

**Ценность заметки:** это готовый реальный пример полного цикла решения по C.11 (все 8 шагов процедуры, а не только framing/triage, как в approach.md), применённый к конкретной рабочей задаче - хороший референс для будущей доработки DPF/LPF (framework scale test, следующий шаг проекта).
