# Уровни детализации: одна таблица, в которой смешались четыре отношения

> *Черновик подготовлен при участии IWE / Claude по заданию R3.4:Mod3 резидентуры «Рабочее моделирование в инженерии и менеджменте», со сверкой через FPF Library (A.1, A.2, A.6.H, A.15.1, C.30.ASV).*

Продолжаю сквозное задание R3.4. Описание - чек-лист-шаблон «Как выглядит „хорошо“ для контроля устранения проблем качества данных». Заказчик - продукт-менеджер: ему нужно убедиться, что новая система готова играть свою роль в надсистеме. Адресат - проектная команда внедрения. Глоссарий к этому описанию был в предыдущем посте.

Теперь задача R3.4:Mod3 - определить уровни детализации: на какие части разбить объект описания и где остановиться.

## С чего начал: процесс - не система

Первое, что пришлось поправить, - сам объект. «Контроль устранения проблем качества данных» звучит как процесс. Урок R3.4:7 прямо говорит: системой называем не процесс, а то, что этот процесс выполняет. Поэтому на Уровне 1 - **система контроля устранения проблем качества данных**: люди, настроенная платформа DG/DQ и правила их работы.

## Первая версия и что с ней было не так

Первая таблица выглядела убедительно: подсистемы, под ними правила, пороги, записи о проблемах, роли стюарда и владельца, этапы цикла, закрытие. Всё «относится к системе».

Проверка по FPF показала, что в одной таблице смешались четыре разных отношения:

- **описания** (правило, порог, запись о проблеме, модель жизненного цикла, соглашение о сроках) - не части системы, а то, чем она пользуется. Раздел регламента не становится деталью системы, которую он описывает;
- **роли** - не части команды. Части команды - люди; роль - то, как человек классифицирован в работе;
- **работа** (прогон проверки, исправление, повторная проверка) - не фаза системы, а то, что система делает во времени. У неё своё разбиение;
- **состояние** («закрыто») - вообще не часть, а атрибут проблемы.

Разбиение по уровням держит только одно отношение - «часть - целое». Остальное пришлось развести по отдельным блокам.

## Итоговые разбиения

Типы по R3.2: КФО - класс функциональных объектов; КМО - класс материальных (конструктивных) объектов; ТЧ - темпоральная часть; О - описание. Описание - в классах, думаем о типовом представителе.

**А. Функциональное разбиение - что делает система**

| Уровень 0 | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|
| Служба управления данными организации :: КФО | Система контроля устранения проблем качества данных :: КФО | Подсистема обнаружения проблем :: КФО | — (дальше - чёрный ящик движка проверок) |
| | | Подсистема учёта и маршрутизации проблем :: КФО | — |
| | | Подсистема координации исправления :: КФО | — |

**Б. Конструктивное разбиение - из чего собрана та же система**

| Уровень 0 | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|
| Организация :: КМО | Система контроля устранения проблем качества данных :: КМО | Настроенная платформа DG/DQ :: КМО | Модуль DQ :: КМО :: КФО (подсистема обнаружения) |
| | | | Модуль реестра и workflow :: КМО :: КФО (подсистема учёта) |
| | | Команда DQ :: КМО | Член команды :: КМО :: КФО (роль: стюард данных) |
| | | | Член команды :: КМО :: КФО (роль: владелец проблемы) |

**В. Метод обработки проблемы - шаги метода, а не выполненная работа**

| Метод | Шаги |
|---|---|
| Метод обработки проблемы (модель жизненного цикла) :: О | Обнаружение (прогон проверки по расписанию) |
| | Назначение (по правилу назначения владельца) |
| | Исправление (в системе-источнике) |
| | Повторная проверка (по порогу) |
| | Закрытие (исправлена / отклонена / риск принят) |

Сначала этот блок был «разбиением работы» на темпоральные части. Но чек-лист - про подготовку к запуску, а до запуска выполненной работы ещё нет. Есть метод: этапы, переходы, ответственные. Работа появится в эксплуатации, когда каждая проблема будет обрабатываться по этому методу.

**Г. Описания, которыми система пользуется (не части)**

Правило качества данных :: О (порог - его часть), запись о проблеме :: О, модель жизненного цикла :: О, соглашение о сроках :: О.

## Почему именно эти уровни

- **Уровень 0** нужен из-за цели заказчика: «готова играть роль в надсистеме» нельзя проверить, не видя надсистему и функцию, которую система для неё выполняет.
- **Уровень 2** - уровень, на котором работает адресат: команда внедрения настраивает обнаружение, реестр и маршрутизацию, назначает людей на роли.
- **Уровень 3** - последний прозрачный: модули платформы и люди в ролях - ровно то, что будут проверять пункты чек-листа.
- **Ниже не идём.** Устройство движка проверок и исправление отдельных записей в системах-источниках для команды внедрения - чёрный ящик. Тест из урока: фраза «проверили, что у каждой проблемы назначен владелец» звучит осмысленно для адресата, а «проверили план выполнения SQL-запроса правила» - уже нет.
- **Системы-источники, наборы и элементы данных** - то, с чем работает система, а не её части. Они появятся в следующем задании как отношения: «правило проверяет элемент данных», «исправление выполняется в системе-источнике».

## Что вынес

Таблица уровней кажется самым простым шагом, но именно в ней легче всего незаметно смешать «из чего состоит», «чем пользуется», «кем укомплектовано» и «что делает». Если в разбиение попадает регламент, роль или этап процесса - это сигнал, что отношение подменилось. Функциональное и конструктивное разбиения при этом нужны оба: чек-листу важно и что система должна делать, и кто и на чём это делает.
