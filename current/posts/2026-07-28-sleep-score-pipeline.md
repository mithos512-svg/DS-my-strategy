# Как я подключил sleep score к своей системе самоорганизации в IWE

Коротко: захотел, чтобы данные сна из Apple Watch сами попадали в мою личную
систему трекинга на GitHub — без ручного переписывания цифр каждое утро. Получилось,
но по дороге пришлось разобраться с базовой аутентификацией GitHub API, форматом
base64, слэшами в датах, ломающими пути к файлам, и содержательной ошибкой
в формуле sleep score, которую сначала предложил Claude.

## С чего всё началось

Система уже существовала: репозиторий `DS-my-strategy` на GitHub, в котором
Claude через IWE ведёт мой ежедневный дневник — вес, питание, инвестированное
время, неудовлетворённости дня. Всё это открывается и закрывается по ритуалу
Day Open / Day Close, правила которого зафиксированы в отдельном файле
`memory/day-rhythm-config.md`.

Не хватало одного — сна. Apple Watch и так собирает фазы сна (Core, Deep, REM),
но эти данные жили только в приложении Health, никак не пересекаясь с остальной
системой.

## Шаг 1 — Shortcuts как мост

Идея простая: Shortcuts на iPhone умеет читать данные из Health и делать сетевые
запросы. Значит, можно собрать автоматизацию, которая:

1. Достаёт из Health длительность фаз сна за последние сутки
2. Кодирует их в текст
3. Отправляет через GitHub API прямо в репозиторий

Идея звучала просто, реализация — нет. Первые попытки упирались то в неверный
формат даты (Shortcuts не даёт готового пресета "вчера" для фильтра Health-данных,
пришлось вручную собирать `Current Date` минус один день), то в саму отправку —
GitHub API принимает содержимое файла только в виде **base64**, и любая лишняя
строка или неверное имя JSON-поля ломает запрос. Один раз ошибся в имени ключа
(`content up` вместо `content`), один раз — в самой кодировке (перенос строки
внутри base64-строки, который GitHub не прощает).

Отдельно повеселила дата в пути к файлу: если её формат содержит слэши
(`27/07/2026`), GitHub воспринимает их как разделители папок — вместо одного
файла получаешь три вложенные директории. Решение — формат `yyyy-MM-dd` с
дефисами вместо слэшей.

## Шаг 2 — не считать в Shortcuts

Первая рабочая версия сразу считала округление и score прямо внутри Shortcuts —
неудобно: интерфейс мобильного конструктора действий не располагает к математике
из нескольких шагов. Решение — разделить ответственность:

- **Shortcuts** отправляет только сырые секунды в `current/health-log/raw/`
- **GitHub Action** ловит коммит в эту папку и запускает Python-скрипт, который
  считает минуты и sleep score, и коммитит уже готовый файл в `current/health-log/`

Это оказалось удобнее по всем параметрам — логику проще редактировать текстом
в репозитории, чем тыкать в телефоне, и она версионируется вместе с остальным
кодом.

## Шаг 3 — формула score: от произвольной эвристики к обоснованной

Первую формулу score предложил Claude — я попросил вариант расчёта, и вот что
получил изначально:

```
score = (Deep×2 + REM×1.5 + Core×1) / total_minutes × 100
```

Идея — что глубокий и REM-сон "весят" больше лёгкого. На практике формула
выдала **129 из 100** — очевидно неправильно. Причина в том, что при весах
больше единицы взвешенная сумма всегда превышает знаменатель, если в сон входит
хоть немного Deep или REM. Первое исправление — нормировать не на общее время сна,
а на максимально возможное значение:

```
score = (Deep×2 + REM×1.5 + Core×1) / (total_minutes × 2) × 100
```

Диапазон стал честно ограничен 0–100, но появился второй вопрос: а откуда вообще
взялись веса 2 / 1.5 / 1? Ответ — ниоткуда, это была эвристика "на глаз", ничем
не подкреплённая. Решил проверить, есть ли более обоснованный подход.

**Что нашли в исследованиях и у трекеров:**

- Норма доли глубокого сна (N3) для взрослых — обычно называют диапазон **13-23%**
  от общего сна ([Sleep Foundation](https://www.sleepfoundation.org/stages-of-sleep/deep-sleep),
  со ссылкой на Medscape).
- Норма доли REM-сна — **20-25%** от общего сна, устойчивый ориентир для взрослых
  ([Sleep Foundation](https://www.sleepfoundation.org/stages-of-sleep/deep-sleep)).
- Академическое исследование составов сна называет чуть более узкие ориентиры:
  N1 3-8%, N2 45-55%, N3 (deep) 15-20%, REM 20-25%
  (González-Naranjo et al., 2019, через [arXiv:2403.13544](https://arxiv.org/pdf/2403.13544)).
- Готовые трекеры не взвешивают минуты произвольными коэффициентами, а сравнивают
  фактическую долю каждой фазы с целевым диапазоном: Oura Ring, например, даёт
  "оптимальный" балл за компонент Deep/REM при достижении примерно 90+ минут этой
  фазы ([Oura blog](https://ouraring.com/blog/sleep-score/)). Похожую логику —
  сравнение факта с типичным здоровым диапазоном по нескольким компонентам
  (длительность, эффективность, латентность, % REM/Deep) — использует и открытый
  калькулятор sleep score
  ([healthcalculatoronline.com](https://healthcalculatoronline.com/sleep-score-calculator/)).

**Итоговая формула** — среднее трёх компонент, каждая штрафует за отклонение от
целевого диапазона в обе стороны (а не просто "чем больше, тем лучше"):

```python
deep_pct = Deep / total_minutes × 100
rem_pct  = REM  / total_minutes × 100

deep_score = 100 - min(|deep_pct - 18| / 10, 1) × 100      # цель ~18% (центр 13-23%)
rem_score  = 100 - min(|rem_pct  - 22.5| / 5, 1) × 100     # цель ~22.5% (центр 20-25%)
duration_score = min(total_minutes / 420, 1) × 100          # цель 7ч = 420 мин

sleep_score = (deep_score + rem_score + duration_score) / 3
```

Разница ощутимая: для ночи 28.07 (4ч24мин, Deep 30 мин, REM 92 мин) старая
"эвристика" выдавала 64/100, новая формула — **32/100**. Оно и понятно: короткая
ночь с перекосом в REM (35% вместо нормальных 20-25%) и нехваткой Deep (11%
вместо 13-23%) — это плохой сон, и старая формула это не показывала, потому что
просто плюсовала любые минуты REM/Deep с большим весом, не сверяясь ни с какой
нормой.

## Итог

Каждое утро в 10:00 Shortcuts сам забирает данные сна за прошедшую ночь и
отправляет их в GitHub. Action пересчитывает их в читаемый вид со score. А в
конце дня, на Day Close, это стало отдельным пунктом ритуала — Claude читает
свежий файл и показывает мне длительность сна и score, вместе с остальной
сводкой дня.

Ничего революционного технически — Shortcuts, GitHub API, немного Python — но
именно комбинация из простых частей закрыла дыру, которая раньше означала
"ручками переписывать цифры из одного приложения в другое", а теперь просто
работает сама. А формула score — маленькое напоминание, что даже "разумная на
вид" эвристика от ИИ стоит сверять с реальными источниками, прежде чем доверять
ей цифры о себе.
