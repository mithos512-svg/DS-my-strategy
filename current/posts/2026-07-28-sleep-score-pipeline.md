# Как я подключил sleep score к своей системе самоорганизации в IWE

Коротко: данные сна из Apple Watch теперь автоматически попадают в личную систему
трекинга на GitHub — без ручного переноса цифр каждое утро. В процессе реализации
пришлось разобраться с базовой аутентификацией GitHub API, форматом base64,
слэшами в датах, ломающими пути к файлам, и содержательной ошибкой в формуле
sleep score, которую изначально предложил Claude.

## С чего всё началось

Система уже существовала: репозиторий `DS-my-strategy` на GitHub, в котором
Claude через IWE ведёт ежедневный дневник — вес, питание, инвестированное время,
неудовлетворённости дня. Всё это открывается и закрывается по ритуалу Day Open /
Day Close, правила которого зафиксированы в отдельном файле
`memory/day-rhythm-config.md`.

Не хватало одного компонента — сна. Apple Watch собирает фазы сна (Core, Deep,
REM), но эти данные оставались только в приложении Health, никак не пересекаясь
с остальной системой.

## Шаг 1 — Shortcuts как мост

Идея: Shortcuts на iPhone умеет читать данные из Health и выполнять сетевые
запросы. На основе этого можно собрать автоматизацию, которая:

1. Забирает из Health длительность фаз сна за последние сутки
2. Кодирует их в текст
3. Отправляет через GitHub API в репозиторий

Реализация оказалась сложнее идеи. Первые попытки упирались то в неверный формат
даты (Shortcuts не предоставляет готового пресета "вчера" для фильтра
Health-данных, пришлось вручную собирать `Current Date` минус один день), то в
саму отправку — GitHub API принимает содержимое файла только в виде **base64**, и
любая лишняя строка или неверное имя JSON-поля ломает запрос. В одном случае была
ошибка в имени ключа (`content up` вместо `content`), в другом — в самой
кодировке (перенос строки внутри base64-строки, который GitHub не допускает).

Отдельная сложность возникла с датой в пути к файлу: если её формат содержит
слэши (`27/07/2026`), GitHub интерпретирует их как разделители папок — вместо
одного файла создаются три вложенные директории. Решение — формат `yyyy-MM-dd` с
дефисами вместо слэшей.

## Шаг 2 — вычисления вне Shortcuts

Первая рабочая версия сразу считала округление и score внутри Shortcuts — это
оказалось неудобно: интерфейс мобильного конструктора действий плохо приспособлен
для многошаговых вычислений. Решение — разделить ответственность:

- **Shortcuts** отправляет только сырые секунды в `current/health-log/raw/`
- **GitHub Action** реагирует на коммит в эту папку и запускает Python-скрипт,
  который считает минуты и sleep score и коммитит готовый файл в
  `current/health-log/`

Такое разделение оказалось удобнее по всем параметрам: логику проще
редактировать текстом в репозитории, и она версионируется вместе с остальным
кодом.

## Шаг 3 — формула score: от произвольной эвристики к обоснованной

Первую формулу score предложил Claude в ответ на запрос варианта расчёта:

```
score = (Deep×2 + REM×1.5 + Core×1) / total_minutes × 100
```

Идея заключалась в том, что глубокий и REM-сон "весят" больше лёгкого. На
практике формула выдала **129 из 100** — очевидная ошибка. Причина в том, что при
весах больше единицы взвешенная сумма всегда превышает знаменатель, если в сон
входит хоть немного Deep или REM. Первое исправление — нормировать не на общее
время сна, а на максимально возможное значение:

```
score = (Deep×2 + REM×1.5 + Core×1) / (total_minutes × 2) × 100
```

Диапазон стал корректно ограничен 0-100, но остался открытым вопрос об источнике
самих весов 2 / 1.5 / 1. Ответ — таких оснований не было, это была
интуитивная оценка. Дальнейшим шагом стала проверка более обоснованного подхода.

**Данные из исследований и практики трекеров:**

- Норма доли глубокого сна (N3) для взрослых обычно указывается в диапазоне
  **13-23%** от общего сна ([Sleep Foundation](https://www.sleepfoundation.org/stages-of-sleep/deep-sleep),
  со ссылкой на Medscape).
- Норма доли REM-сна — **20-25%** от общего сна, устойчивый ориентир для взрослых
  ([Sleep Foundation](https://www.sleepfoundation.org/stages-of-sleep/deep-sleep)).
- Академическое исследование состава сна называет более узкие ориентиры: N1
  3-8%, N2 45-55%, N3 (deep) 15-20%, REM 20-25%
  (González-Naranjo et al., 2019, через [arXiv:2403.13544](https://arxiv.org/pdf/2403.13544)).
- Коммерческие трекеры не взвешивают минуты произвольными коэффициентами, а
  сравнивают фактическую долю каждой фазы с целевым диапазоном: Oura Ring, к
  примеру, присваивает оптимальный балл компоненту Deep/REM при достижении
  примерно 90+ минут этой фазы ([Oura blog](https://ouraring.com/blog/sleep-score/)).
  Аналогичный принцип — сравнение факта с типичным здоровым диапазоном по
  нескольким компонентам (длительность, эффективность, латентность, % REM/Deep)
  — используется в открытом калькуляторе sleep score
  ([healthcalculatoronline.com](https://healthcalculatoronline.com/sleep-score-calculator/)).

**Итоговая формула** — среднее трёх компонент, каждая штрафует за отклонение от
целевого диапазона в обе стороны, а не только за недобор:

```python
deep_pct = Deep / total_minutes × 100
rem_pct  = REM  / total_minutes × 100

deep_score = 100 - min(|deep_pct - 18| / 10, 1) × 100      # цель ~18% (центр 13-23%)
rem_score  = 100 - min(|rem_pct  - 22.5| / 5, 1) × 100     # цель ~22.5% (центр 20-25%)
duration_score = min(total_minutes / 420, 1) × 100          # цель 7ч = 420 мин

sleep_score = (deep_score + rem_score + duration_score) / 3
```

Разница в результате существенная: для ночи 28.07 (4ч24мин, Deep 30 мин, REM 92
мин) прежняя эвристика выдавала 64/100, новая формула — **32/100**. Это точнее
отражает качество ночи: короткая продолжительность сна с перекосом в REM (35%
вместо нормальных 20-25%) и нехваткой Deep (11% вместо 13-23%). Прежняя формула
не показывала эту проблему, поскольку суммировала минуты REM/Deep с повышенным
весом без сверки с какой-либо нормой.

## Итог

Каждое утро в 10:00 Shortcuts автоматически забирает данные сна за прошедшую
ночь и отправляет их в GitHub. Action пересчитывает их в читаемый вид со score.
На Day Close это стало отдельным пунктом ритуала — Claude читает актуальный файл
и показывает длительность сна и score вместе с остальной сводкой дня.

Технически ничего сложного — Shortcuts, GitHub API, немного Python, — но именно
эта комбинация простых частей закрыла разрыв, который раньше означал ручной
перенос цифр из одного приложения в другое. Отдельный вывод касается самой
формулы score: даже правдоподобная на первый взгляд эвристика от ИИ требует
проверки по внешним источникам, прежде чем на неё можно полагаться.
